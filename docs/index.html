Design

One APK in, one database out

How Sextant should turn every byte of an APK into structured, cross-linked data in a single pass, so that any question (an app name, an icon path, which string a layout uses) is a lookup instead of a re-read.

28 Oct 2026·Measured on real APKs from the test corpus·12 min read

In one minute

✓

Recommendation: make one SQLite file the only product of extract, keyed by the APK's SHA-256 and cached. Every CLI command and the MCP server read only that file. No JSONL, no output folder: APK in, SQLite out.

  • Store: SQLite. One file, every language reads it, agents already speak SQL, and full-text search plus recursive queries are built in. Why not a graph database →
  • Model: four layers. Files (every ZIP entry), raw (every XML node and attribute, every resource table entry, every dex item), entities (components, strings, layouts, classes, …), and links (one edge table that ties everything together). →
  • Join key: the resource ID (0x7f…). Manifest, layouts, menus, styles and code all point at resources by that number. Today the code side is missing. →
  • Speed: getting the app name takes 2.2 s from the APK and 7 ms from the database, about 320× faster. →
  • “100%” becomes a checkable promise: a coverage table that says, for every file in the APK, which decoder read it. →

1Where we are today

Sextant already does most of this. sextant extract reads the manifest, resources, dex code, native libraries and signing, and used to write about 35 JSON and JSONL files plus an index.sqlite with 41 tables. Since step 3 of Mission SQLite, one .sqlite file is the whole output. Commands like find, class and callers query that index. So the question isn't “should we build a database”. It's “what should the database be, and what should it stop being”.

I measured the current design on four apps from the test corpus:

What works well

  • Normalized code tables (classes, methods, calls with integer IDs) and a trigram full-text index. Cross-link queries on Nextcloud return in 5–17 ms.
  • Resource references keep both forms, raw (@string/pick_file) and resolved (“Pick a file”).
  • Deterministic output, golden-file tests, and checks against aapt2 and dexdump.

2What earlier tools taught us

APK tools have grown in three waves: decode to files, then decode to objects in memory, then extract to a database and query it. The third wave comes from general code analysis, not Android, and it's the one that fits what you're describing.

2009
smali / baksmali, dex2jar
Turn dex into assembly text or a JAR for Java decompilers.
a lossless, low-level view is always needed as the fallback. Sextant keeps it with sextant smali.
2010
apktool
Decodes resources back into a res/ folder you can read and rebuild.
files are good for people and diffs, but every question becomes a grep across thousands of files.
2011
Androguard
A Python object model of the APK with cross-references, saved as a pickled session.
cross-references are what make analysis useful, but a session that only one language can open locks other tools out.
2013
jadx
Decompiles to Java, with a GUI, search and “find usages”.
people love “find usages”. It's a cross-link query, and it should work across code and resources.
2014
FlowDroid (Soot), MobSF
Taint analysis over a call graph; one-click security reports.
deep analysis needs a call graph with virtual dispatch. Reports are fine for humans, but they're a dead end for scripts.
2014
Joern: code property graphs
Merges syntax tree, control flow and data flow into one graph you can query.
putting every kind of node and edge in one graph is what makes queries across kinds possible.
2014
osquery
Exposes the operating system as SQL tables.
SQL as the universal question language works, even for non-database people.
2015 → 2019
Kythe (Google), LSIF (Sourcegraph)
Language-neutral cross-reference graphs: every symbol has a stable ID, edges are typed.
stable IDs for every entity are what let separate tools link to the same thing.
2019
CodeQL (Semmle, then GitHub)
Extract source into a database once, then run any number of queries over it.
“extract once, query forever” is the proven model. The extractor is the hard, valuable part.
2021
Glean (Meta)
Stores code facts in a database with a schema and derives new facts from existing ones.
keep raw facts and derived facts apart, so derived ones can be rebuilt without re-extracting.
2026
Sextant
Already extracts to SQLite. The next step is to make that database complete, cached and fully linked.
i

No Android tool fully combines the third-wave ideas (one database, stable IDs, raw vs derived facts, a coverage check) with resource-level decoding. That's the opening for Sextant.

Why SQLite wins, point by point
  • One file, no server. You can copy it, attach it to a ticket, or hand it to an agent. A graph database needs a running service.
  • Every language reads it: Kotlin, Python, Go, the sqlite3 shell, Datasette, DuckDB (which can attach SQLite directly).
  • Graphs fit fine. Recursive common table expressions walk call graphs and resource chains. Sextant's callers and reach already do this.
  • Search is built in through FTS5 with trigrams, which is already used.
  • Agents know SQL better than Cypher or Datalog, and can read the schema with one query.
  • It's already there. The change is an evolution, not a rewrite.

Where SQLite is weaker: heavy analytics across hundreds of apps at once. ATTACH covers dozens of app databases in one query, which is enough for Sextant; anything bigger is out of scope.

4The data model

The model should be layered, so each layer has one job and one owner. The lower two layers are facts read from the APK; the upper two are facts Sextant works out. That split is Glean's lesson: when Sextant learns a new SDK signature, it rebuilds the derived layer from the database without opening the APK again.

The rules that make it work

  1. Every entity has a stable text key, the same in every run and every app version: res:string/app_name, cls:Lcom/x/Login;, m:Lcom/x/Login;->go()V, cmp:com.x.MainActivity, file:res/BW.xml. Integer IDs stay for speed inside the file; the text key is what diff, agents and the desktop app pass around. (Kythe and LSIF lesson.)
  2. No JSON arrays for things you'd want to join on. Intent filters, layout views, menu items and style items get real rows. JSON stays only for opaque blobs nobody filters by.
  3. Resource configurations are rows, not copies. res_values(res_id, config, value) keeps fr, night and sw600dp next to the default, so “which strings are missing in German” is one query.
  4. Keep raw and resolved side by side, as Sextant already does for menus: raw = @string/x, ref_id = 0x7f12…, resolved = "Pick a file".
  5. Every fact says where it came from: file, and offset or XML node. A finding is only as good as its evidence.
Schema sketch of the new core tables
-- 1 · Files: every ZIP entry, so "100%" is checkable
CREATE TABLE files (id INTEGER PRIMARY KEY, path TEXT UNIQUE, size INT, compressed INT,
  crc32 INT, sha256 TEXT, type TEXT, parsed_by TEXT);   -- parsed_by NULL = nobody read it

-- 2 · Raw: the resource table and every binary XML file, losslessly
CREATE TABLE res_entries (res_id INTEGER PRIMARY KEY, type TEXT, name TEXT, package TEXT);
CREATE TABLE res_values (res_id INT, config TEXT, kind TEXT, raw TEXT, value TEXT,
  ref_id INT, file INT REFERENCES files(id));
CREATE TABLE xml_nodes (id INTEGER PRIMARY KEY, file INT, parent INT, idx INT, tag TEXT, depth INT);
CREATE TABLE xml_attrs (node INT, ns TEXT, name TEXT, raw TEXT, type TEXT, value TEXT,
  ref_id INT);                                          -- ref_id = the 0x7f… it points at

-- 3 · Entities: one registry so anything can point at anything
CREATE TABLE entities (id INTEGER PRIMARY KEY, kind TEXT, key TEXT UNIQUE, label TEXT);

-- 4 · Links: one edge table, with evidence
CREATE TABLE links (src INT, rel TEXT, dst INT, file INT, node INT, method INT, offset INT);
CREATE INDEX links_src ON links(src, rel);
CREATE INDEX links_dst ON links(dst, rel);

The existing typed tables (calls, field_refs, components, …) stay for the hot paths. links is the one place that connects kinds, so a generic “what links here” works for everything.

5Cross-links: the part that makes it powerful

An APK is a graph that's been flattened into a ZIP. The resource ID is the thread that ties it back together.

The manifest, every layout, menu, style and navigation graph, and the code all refer to resources by the same 32-bit number, 0x7fTTEEEE (package, type, entry). Decode that number everywhere, and every kind of file links to every other.

Closing the code → resource gap

In a release build, R8 removes the R classes and puts the numbers straight into the bytecode (const v0, 0x7f12003a). Binary Eye has zero R$ classes, so today Sextant can't tell which method shows which string. Nextcloud keeps its R fields, with 9,363 field reads, so it half works there. Both cases are easy to cover:

  • Constants: while reading dex, record every const literal whose value is a known resource ID from resources.arsc. Checking against the real ID table keeps false matches near zero.
  • R fields: map R$string.app_name reads to the same resource, using the field's constant value.
  • Call context: keep the callee that receives it (setContentView, getString, inflate), so a link is labelled inflates or shows_text, not just “uses”.
✓

Step 4 result: strings that looked unused dropped from 1,409 to 159 in Nextcloud (of 1,945) and from 313 to 58 in Binary Eye (of 497), once code counts as a referrer. Nextcloud has 6,943 code → resource links, Binary Eye 1,032.

The questions this answers

Your example, “which strings.xml key is used in which layout”, becomes one join. Joins can also chain across kinds:

-- Which exported screens show text that mentions "password", and in which languages is it missing?
SELECT c.key AS screen, s.key AS string, missing.locales
FROM entities c
JOIN links inf ON inf.src = c.id AND inf.rel = 'inflates'        -- screen → layout
JOIN links txt ON txt.src = inf.dst AND txt.rel = 'shows_text'   -- layout → string
JOIN entities s ON s.id = txt.dst
JOIN missing_translations missing ON missing.res = s.key
WHERE c.kind = 'component' AND c.exported AND s.label LIKE '%password%';

Translation

Which strings are missing in each locale, and which screens show them.

Dead resources

Resources nothing points at, counting code too, so the list can be trusted.

UI map

Activity → layout → views → strings and icons: a full screen inventory without running the app.

Security

Exported component → its class → methods it reaches → WebView or crypto calls.

Theming

Which screens use which theme, and which colors change in night.

Version diff

Stable keys make “what changed between 4.2 and 4.3” a set difference.

6The single-shot pipeline

“Single shot” means the APK is opened once and nothing ever needs to open it again for a fact. The order matters, because each step needs the one before it:

  • Write once, index last. Bulk-insert into tables with no indexes inside one transaction, then build the indexes. This is the fastest way to load SQLite.
  • Write to a temp file, then rename. A crash or Ctrl-C never leaves a half-built database that looks complete.
  • Expensive layers on demand. Decompiled Java takes seconds per class, so it isn't part of the single shot. When source decompiles a class, it saves the result in a decompiled table, so the second request is instant.
  • Version stamps. meta stores the extractor version and the derive version separately. A new Sextant release that only improves SDK detection re-runs step 5 in seconds instead of a full extract.

7Instant answers: the cache

You said the app name should be ready-made, like a database entry. Here is what that's worth, measured on Binary Eye:

The proposal is a content-addressed cache, the same trick Git and Nix use:

  1. Any command given an APK computes its SHA-256 (about 20 ms for 8 MB).
  2. If ~/.cache/sextant/<sha256>.db exists and its version matches, the command uses it. It's a lookup.
  3. If not, Sextant runs the single-shot extract once, saves the file, and then answers.

So sextant info app.apk is slow the first time and instant every time after, with no folder to manage. sextant extract app.apk -o app.sqlite writes the same file wherever you want it. Two different APKs can never share a database by mistake, because the key is their content, not their file name.

!

The remaining 650 ms is JVM start-up. For true instant answers from the CLI, the options are a GraalVM native image, or keeping a small daemon running. The desktop app and the MCP server already stay running, so they get the 7 ms path for free.

8What “100%” really means

“Everything the APK has” needs a definition you can check, otherwise it can't be tested. The proposal: every byte belongs to a file row, and every file row says who read it.

LevelMeaningExample
L0 ListedPath, size, hash and type are recordedan unknown .bin in assets/
L1 DecodedContents are turned into rows, losslesslyevery node and attribute of res/layout/main.xml
L2 LinkedRows are connected to other entitiesthat layout's @string and its activity
L3 UnderstoodSextant draws conclusions from it“this layout is a login form”

sextant coverage app.db would print a short table: entries per type and the share at each level. “100%” then means 100% at L0, and L1 for every known format. It's an honest number that can go in CI, and the existing corpus of 46 real APKs is exactly the test set to measure it on.

Formats still to decode losslessly
  • Every binary XML attribute, including unknown ones and their typed values (dimension, color, enum, flags).
  • META-INF/*.version, *.kotlin_module, *.properties, service loader files (META-INF/services/*).
  • Baseline profiles (assets/dexopt/baseline.prof): they list the methods the app runs at start-up.
  • Fonts, raw resources, databases and nested APKs, ZIPs or dex files inside assets/: list, hash, and recurse where it makes sense.
  • Splits of a bundle (.apks, .xapk) as one app with a split column on files.

9From an AI agent's point of view

An agent has a small context window, pays for every token, and can't see a GUI. What helps it most is different from what helps a person:

One handle

“Here's app.db” is all it needs. One file, nothing else to explore.

Self-describing schema

A schema_docs table inside the database explains every table and column, so the agent learns it with one query.

Search → show → links

Three moves cover almost everything: find an entity, see it, follow its links. Each returns a stable key it can pass on.

Small answers

Counts first, with --limit and pagination. Long values are cut with a note saying how to get the rest.

Evidence in every answer

File and offset or XML node, so the agent can cite it and a person can verify it.

Read-only SQL

The escape hatch for questions no tool anticipated. Already exists as sextant sql.

→

The MCP server should get a generic links(key, rel?, direction?) tool. With it, an agent can walk from a string to a layout to an activity to a method without knowing any table names.

10From a power user's point of view

  • Many apps at once. SQLite's ATTACH opens several app databases in one session: “which of my 46 apps ship OkHttp below 4.12” is one query.
  • Saved queries. sextant q unused-strings app.db runs a named SQL file. Users can add their own, the way CodeQL query packs work.
  • Familiar tools. The sqlite3 shell, Datasette (a web UI for any SQLite file), Python and pandas all work out of the box.
  • Desktop app on the same file. The desktop app, CLI and MCP all read one database, so they can never disagree.

✓

In short: Sextant already has the hard part, a careful extractor tested on real apps. The design change is to treat the database as the product: complete (every file), connected (every resource ID decoded everywhere, including code), cached (by content hash) and self-describing (so agents need no manual).
